# Afterhours 16 — v0.5 Early Alpha: graphics and physics overhaul

**Revised plan, Oct 9, 2026.** This replaces the v0.4-era `docs/V0.5-PLAN.md` and widens it from "mocap on the existing engine" to a decision about the engine, the physics and the motion itself. It is written for review: section 2 lays out four ways to proceed, section 3 says which one I recommend and why, and the rest is the plan for that path. Nothing has been changed in the game yet.

## 1. Where v0.4.7.5 leaves us, and what v0.5 has to do

What exists today is a browser game: a from-scratch WebGL2 renderer (`client/js/gfx`, ~115 KB), procedural athletes and a procedural animator (`client/js/char`, ~250 KB), a 60 Hz deterministic simulation that also runs headless in Node (`client/js/sim`, ~420 KB: rules, ball flight, shot model, AI, builds, ratings, badges, the AI world and the Pro Run league), procedural parks and arenas (`client/js/world`, ~155 KB), the match session, park hub, cameras and HUD (`client/js/game`, ~230 KB), DOM menus (`client/js/ui`, ~250 KB plus ~100 KB of CSS), a Python/SQLite service that owns accounts, VC, progression and the catalog, and a Go launcher that wraps Edge/Chrome in an app window. 148 Node tests and 40 Python tests cover it.

What v0.5 has to deliver, in David's words: a version that looks like a different game, with realistic human movement and realistic ball/rim/body physics with very accurate collisions, performance good enough to plan multiplayer around, no sacrifice of the core game built so far, and a build that can open to testers. The browser is something he wants to leave eventually anyway.

Three facts shape the choice below:

1. **The visual jump comes from assets and motion, not from renderer features.** Real meshes with real skin and cloth shading, and recorded human motion, are what separate v0.4 from "a different game". Any of the four paths can load them; they differ in how much of that machinery we have to write ourselves.
2. **The simulation is the crown jewel and must survive intact.** It has hundreds of tuned constants, its own tests and a batch harness whose numbers (FG%, 3P%, dunks, fouls a game) are the definition of "the core game". It has no browser dependencies. Whatever we do, the sim either stays as is or is ported line for line and proven equal with the harness.
3. **The way this project is built matters.** Nearly everything is written in the cloud, tested headless there, and delivered to the PC as files (no shell on the PC, 25 MB per file). A path whose engine cannot be built or tested headless on Linux, or whose assets are binary blobs only an editor can author, would turn Claude from the builder into an advisor and move the work onto David.

## 2. The options

### Option A — Stay on the in-house engine, upgrade it (WebGPU + Jolt WASM + mocap), wrap it in Tauri

Keep every line that exists. Move the renderer to WebGPU (keeping the WebGL2 path as the fallback), add a glTF loader, a clip player, blend trees and motion matching in JS, bring in Jolt Physics through its official WebAssembly build for bodies and contact, and ship with a Tauri or Electron shell so it looks and installs like a native app.

- **Keeps:** 100% of the code, tests, tooling, the Node-side headless sim for a future server, the current delivery workflow.
- **Costs:** we would be writing an animation runtime, an asset pipeline, LODs, GI/AO/SSR, cloth and a physics integration ourselves, in JavaScript, and then throwing most of it away when the move off the browser happens. The browser ceiling stays (one thread of JS for sim + animation, Gamepad API, no native windowing, roughly 2x slower per frame than a native engine at the same scene).
- **Honest verdict:** fastest route to *a* testing build, worst long-term value. It spends the overhaul budget on engine work rather than game work and still ends in a browser.

### Option B — Unreal Engine 5.6/5.7 (maximum fidelity)

Unreal ships, out of the box, exactly the two things v0.5 is about: production Motion Matching (Pose Search databases, trajectory channels, the Game Animation Sample as a reference) and MetaHuman bodies, faces and clothing with body-shape controls, plus Chaos physics, Mutable for character customization, Lumen/Nanite and a dedicated-server networking model. If the only question were "which engine gets the most realistic basketball player on screen", this would be the answer.

- **Costs:** C++ and Blueprints; `.uasset` files are binary and can only be authored in the editor, so Claude cannot write materials, animation blueprints, Pose Search schemas or levels as files. The editor and build toolchain do not run in the cloud workspace, so no headless builds or tests from here. Build times and project sizes are heavy for a solo developer. The 5% royalty starts only above $1M, so money is not the issue; workflow is.
- **Honest verdict:** the best picture, and the path where David does most of the hands-on engine work himself, with Claude writing C++ and documents. If David wants to become an Unreal developer, this is the one. If he wants to keep building the way v0.4 was built, it is the wrong one.

### Option C — Godot 4.6 with C#, and the simulation ported to a pure C# library (recommended)

Godot 4.6 (released January 2026) made Jolt the default 3D physics engine, brought inverse kinematics back as IKModifier3D (TwoBoneIK, FABRIK, CCDIK), rewrote screen-space reflections, and added LibGodot for embedding. It is MIT-licensed, exports a native Windows executable, runs headless on Linux for imports and tests, and stores scenes, resources and shaders as plain text, so Claude can author the whole project as files, build and test it in the cloud, and deliver it to the PC the same way as today.

- **Keeps:** the Python service and database untouched for v0.5 (same HTTP API); the catalog; the music; the sim, ported 1:1 to a C# library with no engine dependency, which is also exactly what the future authoritative game server needs; the shot-model guarantee (made/missed decided first, trajectory solved to match) by porting `ball.js` as our own deterministic solver rather than handing the ball to the physics engine.
- **Adds:** Jolt for player bodies, powered-ragdoll contact reactions, blocks and deflections, loose balls and a soft-body net; a C# motion-matching runtime (the design is already in the old plan; an MIT Godot reference implementation exists to borrow from); glTF characters with morph targets; Godot's Forward+ renderer with baked lightmaps for the parks, SSAO, half-res SSR on hardwood, volumetric floodlights, TAA/FSR and AgX/ACES tonemapping.
- **Costs:** the sim port (~420 KB of JS → C#) and a rebuild of the presentation (renderer, characters, worlds, HUD and menus). The renderer, characters and worlds were being rebuilt in any case; the menus (~250 KB of DOM code) and the park hub / session flow (~230 KB) are the real porting cost that an engine change adds. No built-in motion matching, so we write it (bounded: a KD-tree search over ~30k frames, inertialized blends). Godot's renderer is a step below Unreal's at the top end, which is fine for the "late-console sim, night parks, bloom" look and better for the performance budget.
- **Honest verdict:** the one path that leaves the browser, keeps Claude as the builder, keeps the sim intact for the server later, and spends the overhaul on game content rather than engine plumbing.

### Option D — Unity 6 with C#

Same C# sim port as C, a large asset ecosystem (including purchasable motion-matching packages and basketball animation packs made for Unity's Humanoid rig), text-serialized scenes, and Unity Personal is free under $200k revenue. The editor can run in batch mode on Linux but is several GB, needs an account login to activate, and visual-authoring assets (shader graphs, animator controllers) are awkward to write as files. A reasonable middle if David has a reason to prefer Unity; otherwise C gives the same language and workflow with a lighter, fully open engine and no activation step.

### Option E — Write a native engine from scratch

Mentioned because David raised it: no. The renderer we have is already a from-scratch engine; the lesson of v0.4 is that engine work competes with game work. A native rewrite of it plus a physics integration plus an asset pipeline would consume v0.5 entirely and produce what Godot gives us on day one.

## 3. Recommendation

**Go with Option C: Godot 4.6, C#, Jolt, our own motion matching, the sim ported to an engine-independent C# library, the Python service unchanged.** The reasoning in one paragraph: the browser is leaving anyway, and the cheapest moment to leave it is the moment the presentation is being rebuilt, which is now. Unreal buys the best picture at the price of the workflow that produced the whole v0.4 line in a matter of days; Godot keeps that workflow, ships a native executable, and gives us Jolt and IK built in. The sim, the AI, the economy, the AI world and the Pro Run are data and rules, not pixels, so a line-for-line C# port verified against the existing batch harness carries "the core game" across whole, and that same library becomes the server simulation when multiplayer comes.

**Two guardrails on the recommendation.** First, it is gated: milestone M0 below is a two-stage spike that must prove the sim parity harness, a Jolt ball-vs-rim test and one motion-matched character in Godot before anything else is ported. If the spike fails on performance or on parity, the fallback is Option A, with nothing lost but the spike. Second, "less is more" applies to graphics: the target look is a night park under floodlights with convincing people in it, not Lumen. Baked lighting, a few real-time shadowed lights, good skin and cloth shading and real motion do that; the frame budget is reserved for ten players and the court overview's three live games.

## 4. Motion: how we get realistic human movement

### 4.1 Technique

Motion matching over a library of recorded clips, with the simulation authoritative, is the right technique for a basketball game at this scale and it is what the previous plan already specified. The runtime (C#, in `Afterhours.Anim`):

- **Locomotion:** every 0.1 s, build a query from the sim's future root trajectory (0.33 / 0.66 / 1.0 s ahead, which the sim knows because it owns the player's velocity and intent), current foot positions and velocities and hip velocity; search a KD-tree over the library; switch clips with inertialized blending. This removes the "gamey" starts, stops, cuts and turns. Database by role (on-ball, off-ball offense, defense slide, park walk/jog) so searches stay small.
- **Actions stay gameplay-timed:** jumpers, layups, dunks, passes, blocks and steals are clips time-warped so their markers (dip bottom, takeoff, set point, release, landing; gather steps; ball contact) land exactly on the sim's `takeoff` and `releaseAt`. The green window cannot drift from the picture, same guarantee as today.
- **Layers:** an additive upper-body layer for ball handling (size-ups, dribble moves as short clips) over locomotion; hand IK onto the simulated ball; foot IK with locking (IKModifier3D TwoBoneIK); look-at.
- **Contact:** a powered ragdoll (Jolt motorized constraints) blended in for bumps, screens, box-outs and posters, driven by the sim's collision impulses, so bodies react physically and recover into the next clip. This replaces the additive "hit" spine pose in the old plan with real contact.
- **Fallback:** the v0.4 procedural animator's timings remain the reference implementation and the fallback for actions with no clip yet.

### 4.2 Where the motion data comes from

No single free source covers basketball well, so the plan is a layered library of about 20–30 minutes, built so that everything that ships has clear commercial rights. The pipeline (Blender, scripted) retargets everything onto one game skeleton.

## 5. Physics: what changes and what is deliberately kept

- **Ball flight stays ours.** `ball.js` (gravity, drag, Magnus, torus rim with deterministic per-contact deflection, backboard, bracket, floor restitution and spin coupling, net damping) ports to C# unchanged, with the rim test resolved analytically against the torus every sub-step, so there is no tunnelling and the pre-simulated make/miss stays exact. A ball at 15 m/s moves 25 cm per 60 Hz step; the rim tube is about 2 cm, so an engine-driven ball would need continuous collision anyway, and we would lose the shot-model guarantee. The one upgrade: 8 sub-steps instead of 4 near the rim, and spin on dribble contact.
- **Bodies move to Jolt.** Players become kinematic character bodies (capsule plus a sensor for reach) during normal play; contact impulses from the sim's `collide` / `boxOuts` go through Jolt so bumps, screens and posters resolve against real shapes, and a powered ragdoll takes over for the duration of a stumble, knockdown or hard screen before blending back. Hands and arms get small kinematic capsules so blocks, deflections and poke-aways are shape casts against the actual limb, not a distance check.
- **Loose balls** use Jolt for ball-vs-body deflections (rebounds off hands, bodies and feet) with the ball handed back to our solver the moment it is in free flight toward a hoop.
- **Net and jerseys:** a Jolt soft body for the net (replacing the procedural funnel), verlet or soft-body hems on LOD0 jerseys and shorts only.
- **Determinism:** everything that decides outcomes (ball flight, shot grading, contests, rebounds' target point) stays in our fixed-step C# code. Jolt affects how bodies look when they meet, not who gets the ball. This is also what keeps the future server authoritative and cheap.

## 6. Graphics: scope for "less is more"

- **Characters:** a CC0 MakeHuman/MPFB2 base body retopologized to the game skeleton with morph targets for height, weight, muscle and wingspan (replacing the procedural lofts), face blendshapes so faces read as people, 2K skin sets per tone family with pre-integrated subsurface scattering, separate eyes with refraction, hair cards with alpha-to-coverage. LOD0 ~18k triangles, LOD1 ~7k, LOD2 ~2.5k; budget ~300k character triangles for ten players plus park life. **Stretch option:** MetaHuman bodies and faces are now licensed for use in Godot (free under $1M revenue, no royalty on non-Unreal games), which would be the single biggest visual jump available; the cost is that generating them needs Unreal 5.6 installed on David's PC and Epic's cloud services, and their LOD chain needs taming for ten on court plus the overview. Evaluate in M2 with one character.
- **Clothing:** a modular garment set (jersey, tee, compression, hoodie, shorts, joggers, socks, sleeves, bands, nine shoe models) as meshes fitted to the morphs, with the existing procedural texture painting kept by **baking it offline with the current Node code into PNG atlases**, so all 362 items plus the Pro-Am team branding carry over without re-authoring.
- **Worlds:** the three parks, the Cup park, the arena, the gym and the Crew HQ, rebuilt as Godot scenes. The procedural generators in `venues.js` port to C# `SurfaceTool` so layouts stay identical; props are swapped for modeled ones over time. Lighting: baked `LightmapGI` for static geometry, 3–4 real-time shadowed floodlights per visible court, volumetric fog for the light cones, half-res SSR on hardwood only, SSAO, bloom, AgX/ACES, TAA or FSR 2. No SDFGI, no ray tracing.
- **Performance tiers:** Low to Ultra as today, with the court overview and the AI courts running animation at 15 Hz and LOD2 when not in the main camera. Target: 60 fps at 1080p High on a GTX 1660 / RX 580 class GPU; 1440p on an RTX 3060 class.
- **Effects:** streak fire and lasers as shaders (ported from the current GLSL), green effects as `GPUParticles3D` recreated from the 28 recipes, defensive arrows and the meter as the same designs.

## 9. Risks

- **The sim port drifts.** Mitigated by porting module by module behind the parity harness, with exact ball and grader traces, before any gameplay is built on the port.
- **Motion data quality and rights.** The free layers alone make locomotion good and basketball passable; the own-capture layer is what makes it convincing, and it depends on David recording. Nothing with unclear rights ships.
- **Retargeting onto wildly different builds** (5'7" to 7'3", wingspans to +9"). Motion is retargeted to a normalized rig and the sim's reach stays authoritative for contests, so gameplay does not change with the picture; IK closes the gaps.
- **Performance of the court overview** (three live games). LOD2 plus 15 Hz animation for non-focus courts; the budget is checked at every milestone, not at the end.
- **UI rebuild is the hidden cost** of any engine move. It is scheduled as its own milestone (M5) and the current screens are the spec, so nothing is redesigned at the same time as it is ported.
- **MetaHuman dependence** if chosen: cloud services and an Unreal install for authoring. Kept as an evaluated stretch, with the CC0 body as the plan of record.
- **Tooling on the PC.** Godot's export templates and the .NET SDK are one-time installs; everything else keeps the current file-delivery workflow.
